# Design 75: Planboard — optimistic leg assign/unassign with pending-value indicators

**PBI:** https://github.com/marinusbrink/opentms-next/issues/75
**Status:** draft
**Date:** 2026-11-17
**Depends on:** designs 49 (derived values and live updates), 68 (Planboard commands), 70 (Planboard app), 74 (Planboard review §9 — CalculatingIndicator after save).

## Domain impact

**Lead module: Planning & Execution (frontend only).** No new entities. No new events. No new migrations.

**Decisions relied on:** AD-07 (derived values stored and never calculated on read; screen shows CalculatingIndicator until pushed), AD-18 (application services are the command layer). **Flow: 2** (`02-flows.md` A–D) — this design changes *when the screen reflects step A*, making it happen locally before the round trip to the server.

**Existing derived-value calculators — no new registrations:**

| Calculator | Module | Target type |
|---|---|---|
| `LegRouteCalculator` | Planning & Execution | `PlanningExecution.Leg` |
| `TripCalculator` | Planning & Execution | `PlanningExecution.TransportTrip` |
| `OrderRateLineCalculator` | Financial | `Financial.OrderRateLines` |
| `TripRateLineCalculator` | Financial | `Financial.TripRateLines` |
| `OrderFactCalculator` | Reporting | `Reporting.OrderFact` |
| `TripFactCalculator` | Reporting | `Reporting.TripFact` |

All six are pre-existing. This design shows their pending state on the Planboard and measures how quickly the chain completes after a leg drop.

**New frontend components and hooks:** `useTripCommandQueue`, `usePlanboardOptimisticState`, updated drop handlers in the Scheduler pane and the Legs pane, new drop-target surface on the Legs to schedule pane.

**No backend changes.** The existing Planboard commands from design 68 — `POST /api/planning/planboard/trips/{id}/legs` (assign) and `POST /api/planning/planboard/trips/{id}/legs/remove` (unassign) — are correct as-is. Each accepts a `ConcurrencyStamp`, returns `PlanboardChangeDto { Id, ConcurrencyStamp, LastModificationTime }`, requests trip recalculation via `IDerivedValueScheduler`, and notifies the trip on the record channel.

## API contract

No new endpoints and no changes to existing endpoints. The design relies entirely on two existing commands:

| Command | Route | Input | Returns |
|---|---|---|---|
| Assign legs | `POST /api/planning/planboard/trips/{tripId}/legs` | `{ legIds: Guid[], concurrencyStamp: string }` | `PlanboardChangeDto` |
| Unassign legs | `POST /api/planning/planboard/trips/{tripId}/legs/remove` | `{ legIds: Guid[], concurrencyStamp: string }` | `PlanboardChangeDto` |

A 409 on either command means the stamp is stale. The retry rule: refetch the trip's current stamp from `GET /api/planning/planboard/trips/{tripId}` (scheduler bars endpoint `scheduler/bars?ids=tripId` returns the bar with the current stamp) and retry once. On second 409 or any other server error: rollback the optimistic change and show a toast.

**OpenAPI contract unchanged.** The typed client is not regenerated by this design.

## Migration strategy

Not applicable — no schema changes, no backend changes, no data migration.

## UI design

This design changes three surfaces and adds one new hook layer. All work is in `frontend/src/apps/planboard/`.

### The gap closed by this design

Design 74 §9 introduced: after a command returns, the frontend patches the bar/row from the server response and shows `CalculatingIndicator` until the SignalR push arrives. That is correct but still synchronous with the server: the user sees the leg move only after the 200 ms round trip. PBI 75 moves the visual update to before the round trip, so the leg moves at < 100 ms (a pointer-up handler, no network).

### A. Optimistic state layer — `usePlanboardOptimisticState`

A context value above the panes that tracks per-trip in-flight changes:

```ts
interface PlanningOptimisticState {
  // legs optimistically added to a trip, keyed by tripId
  assignedLegs: Map<string, Set<string>>;
  // legs optimistically removed from a trip, keyed by tripId
  unassignedLegs: Map<string, Set<string>>;
  // trips whose values are locally-pending (CalculatingIndicator on)
  pendingValues: Set<string>;
}
```

**Assign path:**
1. Pointer-up on a Scheduler row/bar or Trips row (< 100 ms, synchronous):
   - Remove the leg ids from the Legs to schedule pane's displayed list.
   - Add the leg ids to the target trip's displayed bar/row.
   - Add the target trip id to `pendingValues`.
   - Enqueue the assign command in the per-trip command queue.
2. Command queue sends `POST trips/{id}/legs` with the latest server stamp.
3. Server responds: update the stored server stamp; remove the leg ids from `assignedLegs` (they are now server-confirmed and will appear in the next fetch); keep `pendingValues` set until the SignalR push arrives.
4. SignalR `recordUpdated` for `PlanningExecution.TransportTrip` arrives: invalidate TanStack queries for the trip; remove trip id from `pendingValues`.
5. On error: see **Error handling** below.

**Unassign path (via Legs to schedule drop or existing row action):**
1. Pointer-up on the Legs to schedule pane (new surface; see §C) or invocation of the existing "Unassign" row action in the Legs pane:
   - Add the leg ids to the Legs to schedule pane's displayed list optimistically.
   - Remove the leg ids from the source trip's displayed bar/row.
   - Add the source trip id to `pendingValues`.
   - Enqueue the unassign command.
2–4. Same as assign path with the source trip's id.
5. On error: see **Error handling** below.

**Leg move (from Legs pane to another trip):**
Treat as an unassign + assign in one round trip, but using the existing `POST /api/planning/planboard/leg/{id}/move` or by chaining unassign and assign commands. The command queue serialises them so the stamp is consistent. The destination trip also enters `pendingValues`.

**Interaction with incoming live updates (another planner's change):**
- For any trip whose command queue is non-empty: ignore `recordUpdated` events for leg-assignment changes on that trip until the queue drains, then apply any queued live updates.
- For all other trips: live updates apply immediately (unchanged from design 70).

### B. Per-trip command queue — `useTripCommandQueue`

```ts
interface TripCommand {
  type: 'assign' | 'unassign';
  tripId: string;
  legIds: string[];
  // assigned at dispatch time from the last confirmed server stamp
  concurrencyStamp: string;
  // localId to match against optimistic state on rollback
  localId: string;
}
```

One queue instance per trip that has in-flight work. The queue holds commands in FIFO order and processes them **one at a time**:

1. Dequeue the first command; send it with the current `concurrencyStamp` (the latest stamp known from the server).
2. On success: update `concurrencyStamp` from the response; dequeue the next command if any.
3. On 409: refetch the trip's current stamp (one `GET scheduler/bars?ids=tripId` call); retry the failed command once with the fresh stamp.
4. On second 409 or any other non-retriable error: **rollback all queued commands for this trip** (see §Error handling) and clear the queue.
5. On network failure: same as step 4; a toast asks the user to retry.

**Why one at a time:** the assign/unassign commands check the concurrency stamp. Sending two commands concurrently with the same stamp guarantees a 409 on the second. By serialising, each command uses the stamp the previous one returned, so the calculator's stamp bumps between commands are absorbed without retries.

**Why local moves are shown immediately despite queuing:** the optimistic state layer shows all queued moves at once; only server confirmation is deferred. The planner sees all three drops immediately; the server processes them in order.

### C. Legs to schedule pane as unassign drop target (new surface)

The Legs to schedule pane (`LegsToSchedulePane`) is an **`OpenTmsGrid`** (`src/apps/planboard/panes/legs-to-schedule/`). It currently acts only as a drag source (payload `application/x-opentms-legs` with `legIds`). This design adds a drop zone.

**Drop payload accepted:** `application/x-opentms-legs` where the payload includes `fromTripId: string` (set by the drag source when the leg is currently assigned). A payload without `fromTripId` (a re-drop from the same pane) is rejected with no visual feedback.

**Drag sources that produce `fromTripId`:**
- The Legs pane (`LegsPane`): every row becomes draggable with a drag handle in the leftmost column; the payload is `{ legIds: [row.legId], fromTripId: focusedTripId }`.
- Existing leg rows in other drag contexts (e.g., legs dragged off a Scheduler bar onto the pane, should the FullCalendar adapter support external drops from bars — see Assumption 3).

**Drop zone presentation:**
- While any drag is in progress with `fromTripId` set, the Legs to schedule pane shows a blue drop-zone border and dim overlay ("Drop here to unassign").
- On drop: trigger the unassign optimistic state transition (§A) and enqueue the unassign command.
- The pane does not need to know the trip's current `ConcurrencyStamp` at drop time — the command queue fetches the latest stamp at dispatch time.

**Existing "Unassign" row action in the Legs pane stays.** It is the accessible, non-drag path and continues to work. It calls the same command queue.

### D. CalculatingIndicator placement

Values that show `CalculatingIndicator` immediately after a leg drop (from optimistic state `pendingValues`):

| Pane / component | Values shown pending |
|---|---|
| Scheduler bar | load factor badge, warning icon (while `pendingValues` contains the trip id) |
| Trips pane row | `cost`, `revenue`, `co2`, `distance`, `loadFactor`, `warnings` columns |
| Map trip-detail card | toll, CO₂, distance, route segments (route is replaced by straight lines while pending) |
| Stops pane | ETA columns |

Values stay pending until `recordUpdated` from `PlanningExecution.TransportTrip` arrives (TripCalculator finished). Financial values (`cost`, `revenue`) may remain pending an extra moment while `OrderRateLineCalculator` and `TripRateLineCalculator` run. If the Financial target type is separately watched by those panes, the indicator stays on until the Financial push too; if those panes watch only the trip target type, the indicator clears after TripCalculator (see Assumption 4).

Design 49's `CalculatingIndicator` and `useDerivedValueStates` are used unchanged. While `pendingValues.has(tripId)` is true before the server confirm, the indicator is driven by the optimistic state directly (not from a `DerivedValueState` row, which may not exist yet). After server confirm, the existing `useDerivedValueStates` hook takes over and continues showing the indicator while the calculator chain runs.

### E. Error handling and rollback

**On server error or second-409:**
- Reverse the leg assignments in `usePlanboardOptimisticState` (move leg ids back to their source).
- Clear `pendingValues` for the trip.
- Drain the remaining command queue for this trip.
- Show a toast (`useToast`): "Failed to update trip — your changes have been reverted." Include a brief reason if the error code gives one (e.g., `PlanningExecution:LegIsStuck` → "One or more legs could not be moved.").

**On partial queue completion (commands 1–2 succeed, command 3 fails):**
- Commands 1–2 are server-committed; only command 3 and any after it are rolled back.
- The optimistic state for commands 1–2 is already reconciled via server response; only command 3's optimistic state is reversed.
- Toast names which legs were not moved.

**Edge cases from intake (each handled explicitly):**

| Edge case | Handling |
|---|---|
| **Stale concurrency stamp** | 409 → one refetch and retry; on second 409 rollback + toast "Could not assign — another change happened, please try again" |
| **Drop outside time window** | Backend returns a warning code; `TripCalculator` writes `OutsideWindow` to the bar; the bar shows the warning marker without a dialog (existing mechanism) |
| **Stuck legs when order is dropped** | Per design 74 §8: movable legs assign, stuck legs stay unplanned; server response `stuck: Guid[]`; toast names stuck legs; optimistic state only moves the movable ones |
| **Rapid successive drops on the same trip** | Per-trip command queue; each drop is shown immediately; server processes in order; a later response never overwrites a newer local change |
| **Routing/calculation failure** | Leg stays assigned (server already committed); `DerivedValueState` shows `Failed`; `CalculatingIndicator` switches to failure icon; Hangfire retries the calculator; assignment is never undone |
| **Browser close while saving** | Browser warns user (existing `beforeunload` on pending mutations); server calculations finish regardless |
| **Another planner's live update during in-flight save** | Live update applies to all other trips; the in-flight trip's leg/assignment state keeps showing the planner's local version until the queue drains; then server state wins |
| **Empty trip after last unassign** | Trip row stays in Trips pane and Scheduler, shown as empty; no auto-removal; no warning (current behaviour per PO) |

### F. Screen states for new surfaces

**Legs pane row (drag handle added):**
- Default: drag handle visible on row hover (matches Trips pane conventions).
- While dragging: `isDragging` class dims the row.
- Permission-denied: `Legs.Update` absent → no drag handle; unassign action hidden (existing rule).

**Legs to schedule pane:**
- Default: drag source only (unchanged).
- During drag of an assigned leg: drop zone border + overlay text shown.
- Empty state (no unplanned legs, but a leg is being dropped): accepts the drop and shows the new leg.
- Error state (unassign fails): toast; leg not added to the pane.

**Optimistic interactions get no optimistic update flag beyond the pending state** (the design does not designate any further optimistic writes for the Financial or Reporting values — they always go through the calculator chain).

## Cost & SLO impact

**Compute:** no change. The optimistic assign calls the same commands at the same frequency. No new Hangfire jobs or background workers.

**Cloud SQL:** no change. The `DerivedValueState` rows and job rows written per assign/unassign are identical to today's.

**SignalR:** no change. The hub groups and push messages are unchanged.

**Performance budgets touched:**

- **Mutations p95 < 500 ms** (the Planboard's 200 ms budget from design 66): the existing commands already meet this. The command queue serialises rapid drops but does not widen the per-command window.
- **Interactive reads p95 < 300 ms**: not changed.
- **Derived-value chain (1 s p95 target, PBI-specific):** this design's k6 measurement will determine whether the target is met. The expected chain for a 30-leg trip:
  - `TripCalculator` (Planning): ~100–300 ms without routing engine (from design 74 measurements).
  - `TripRateLineCalculator` and `OrderRateLineCalculator` (Financial): estimated 150–300 ms combined (two sequential Hangfire jobs, each ~50–150 ms plus outbox/event propagation ~50 ms per hop).
  - Total (non-routing values on screen): estimated 300–600 ms p95, meeting the 1 s target.
  - With routing engine: routing engine latency adds to `TripCalculator`'s run time and is **excluded from the 1 s target** per the PBI. Route geometry, toll and distance values continue showing `CalculatingIndicator` beyond 1 s when routing is in use; this is expected and acceptable.
  - The measurement must confirm the Financial chain conclusion. If the p95 exceeds 1 s, the design addendum will propose chaining the Financial calculators as a single Hangfire continuation rather than through the outbox, which would reduce hop latency by one event round trip (~100 ms).
- **Core flow availability 99.9 %**: this design does not change any availability-critical path.

**Per-tenant margin:** no effect.

## Assumptions

1. **The existing `POST /api/planning/planboard/trips/{id}/legs` command returns the new `ConcurrencyStamp` in the `PlanboardChangeDto` response**, which the command queue uses to send the next queued command. Design 68 specifies this; confirmed in the "As built" section.
2. **The derived-value chain for Planning + Financial (without routing) completes within 1 s p95 at the design 66 volume.** Estimated from design 74 measurements; must be confirmed by the k6 addition. If it fails, the addendum proposes the chaining optimisation.
3. **FullCalendar Scheduler does not expose a native "drag an event off the bar back to an external container" gesture** for leg unassign. As a result, the primary drag-to-unassign surface is the Legs pane row → Legs to schedule pane. If FullCalendar can be made to emit an `onExternalDrop` back to an external zone, it is a later enhancement, not part of this design. The existing "Unassign" row action in the Legs pane is the accessible fallback.
4. **The Trips pane's `cost` and `revenue` columns watch `PlanningExecution.TransportTrip`** (via the existing `useRecordUpdates` hook), not a separate Financial target type. The pending indicator on those columns therefore clears after `TripCalculator` completes. If a future design registers a Financial-type watch on those columns, the pending duration extends to the Financial chain's completion.
5. **The `scheduler/bars?ids=` endpoint returns the current `ConcurrencyStamp` in the bar shape** (design 68 "As built" lists the bar shape including `concurrencyStamp`). The retry path after a 409 uses this endpoint to fetch a fresh stamp.
6. **The routing engine is not configured in development** (confirmed by design 68 Assumption 2). Performance measurements for the 1 s target must be taken on a staging environment with the routing adapter configured or simulated to match design 74's measurement approach.
7. **A partial-queue rollback (commands 1–N succeed, command N+1 fails) leaves the user in a consistent state** because commands 1–N are already server-committed and their legs are on the trip. Only command N+1's legs are rolled back. The user must re-drag those legs if desired; no automatic retry.

## Security quickscan

**No new permissions.** Assign and unassign reuse the existing `PlanningExecution.Legs.Update` permission (checked server-side in `PlanboardAppService`) and the `Apps.Planboard` feature gate.

**No new API surface.** All commands and reads are unchanged. The typed client is not regenerated.

**Input validation (frontend):** leg ids and trip ids are Guids; they are passed through the existing command payloads which are validated server-side. No user-supplied text enters the optimistic state machinery.

**Attack surface:** unchanged — same endpoints, same authentication.

**No personal data.** The optimistic state carries leg ids, trip ids and concurrency stamps only (no names, addresses, driver information). Log lines from the command queue write leg ids and trip ids, not names (constitution rule 5).

**GDPR:** not applicable — no new personal data entities.
